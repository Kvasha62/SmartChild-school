# План разработки SmartChild-school: локально → production на Beget

- Статус: план утверждён для выполнения; production ещё не готов.
- Дата создания: 2026-10-16.
- Основной принцип: сначала закончить и принять локальную версию, только затем настраивать VPS.
- Репозиторий: `Kvasha62/SmartChild-school`.
- Предполагаемый production-хост: VPS Beget, Германия, 1 vCPU, 2 GiB RAM, 10 GiB NVMe, публичный IPv4.
- Предпочтительная ОС VPS: Ubuntu Server 24.04 LTS x86_64, без графической оболочки. Устанавливать её следует только на этапе production после проверки, что на VPS нет нужных данных.

## Правила работы

1. Изменения начинаются с read-only аудита: ветка, HEAD, статус, diff, файлы и результаты последних тестов.
2. Не перезаписывать и не удалять незакоммиченные локальные файлы. Локальная рабочая копия может содержать незапубликованные изменения, отсутствующие в GitHub.
3. Перед каждой логической правкой определить ожидаемый список файлов; после неё просмотреть diff и проверить, что изменено только ожидаемое.
4. Секреты, пароли, токены, приватные ключи, реальные адреса подписчиков и содержимое `.env` не записывать в Git и дневник.
5. Не выполнять commit, push, merge, создание/обновление PR, публикацию или production-действия без явного разрешения пользователя на соответствующий шаг. Для документационного плана это разрешение дано отдельно; дальнейшие изменения требуют своего согласования.
6. Все утверждения о тестах должны опираться на фактический вывод команды или CI. Непроверенное обозначать как «не проверено», ошибки — как блокеры, а не как PASS.
7. Не использовать production-секреты или настоящие адреса пользователей в локальных тестах.
8. Каждый завершённый этап отражать в `docs/DEVELOPMENT-LOG.md`: дата, область работы, основание/коммит, команды и результаты проверок, изменённые файлы, ограничения, решение и следующий шаг.

## Этап 4. Подготовка VPS Beget

Выполняется только после отдельного разрешения на production и подтверждения, что диск можно переустанавливать.

- [ ] Уточнить, какие данные и сервисы уже находятся на VPS; перед переустановкой получить подтверждение пользователя.
- [ ] Установить Ubuntu Server 24.04 LTS amd64 без GUI, если ОС ещё не установлена и пользователь подтвердил очистку диска.
- [ ] Настроить отдельного непривилегированного пользователя, SSH-ключи, запрет небезопасного входа, обновления безопасности и firewall.
- [ ] Открыть только необходимые входящие порты: SSH по выбранной политике, HTTP 80 для перенаправления/ACME и HTTPS 443.
- [ ] Установить Nginx и Node.js LTS, совместимый с требованием проекта (`>=22.12.0`), только если выбранная архитектура действительно требует Node.js на сервере.
- [ ] Раздавать статический `dist/` через Nginx; API запускать отдельной systemd-службой и проксировать только нужный маршрут. Не запускать dev-сервер Astro в production.
- [ ] Хранить приложение, конфигурацию и секреты раздельно; права на секреты — минимальные.
- [ ] Настроить домен/DNS, HTTPS и автоматическое продление сертификата.
- [ ] Настроить ротацию логов, резервное копирование конфигурации и артефактов, мониторинг свободного диска и памяти.

## Архитектура по умолчанию (предварительная, не развёрнутая)

- Сайт: статическая сборка Astro.
- Веб-сервер: Nginx.
- API: существующий Node.js endpoint `/api/lead` как отдельная systemd-служба — только если аудит подтвердит совместимость и необходимость.
- PDF: статический файл в сборке сайта.
- Email и список контактов: один выбранный внешний сервис после сравнения тарифов и требований согласия.
- База данных на VPS: не добавлять без доказанной потребности.
- HTTPS: Let's Encrypt.
- Резервное копирование: конфигурация, релизные артефакты и необходимые данные; никаких паролей/секретов в Git.

## Definition of Done

Локальная версия считается принятой, когда:
- сайт и PDF корректно собираются;
- проверки и тесты выполнены с зафиксированным результатом;
- форма имеет документированный контракт, обработку ошибок и согласий;
- секреты исключены из репозитория и сборки;
- изменения проверены по diff и привязаны к коммиту;
- дневник отражает результаты и следующий конкретный шаг.

Production считается завершённым только после успешной HTTPS-проверки, end-to-end теста формы и PDF, проверки отказного сценария email, резервного копирования и отката.
