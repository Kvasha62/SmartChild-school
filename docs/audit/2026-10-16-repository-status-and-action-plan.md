## 1. Итоговое заключение

Основная ветка имеет успешный GitHub Actions CI для закреплённой ревизии. Статья ЕГЭ о выборе трёх чисел вошла в `main` через PR #2. Документационный PR #4 открыт в Draft и предназначен для сохранения результатов аудита и границ доказательств.

Однако успешная сборка сама по себе не доказывает готовность сайта к публичному использованию. В закреплённой основной ревизии отмечены три блокирующие для запуска проблемы: фиктивные контактные сведения, неподключённая форма заявки и обещанный PDF, отсутствующий в этой ревизии. Поэтому рекомендация на дату отчёта — продолжать разработку, а публичный запуск отложить до закрытия этих блокеров и проверки исправлений.

## 4. Блокирующие замечания основной ревизии

Подробные основания приведены в [аудите Arena](2026-10-15-arena-audit.md) и [независимой проверке](2026-10-15-independent-verification.md). Следующие замечания относятся к закреплённой ревизии `main`, а не ко всем локальным файлам.

### F1. Фиктивные контакты и реквизиты

В исходниках основной ревизии зафиксированы шаблонные контактные данные и заглушка изображения преподавателя. До публичного запуска необходимо заменить их проверенными сведениями либо убрать соответствующие элементы.

**Критерий закрытия:** все отображаемые контакты подтверждены владельцем; фиктивные телефон, домен, Telegram и реквизиты не показываются пользователям.

### F2. Форма заявки не подключена

В основной ревизии форма на главной странице не имеет полноценного серверного обработчика; форма с пустым `action` и неуказанным `method` может отправлять данные через GET в URL по стандартному поведению HTML.

**Критерий закрытия:** POST-обработчик, серверная валидация, понятные сообщения об успехе/ошибке, защита от злоупотреблений и надлежащая обработка персональных данных проверены тестами. Адрес e-mail и другие данные формы не попадают в URL.

### F3. Обещанный PDF отсутствует в основной ревизии

Основная страница обещает бесплатный чек-лист с доставкой по электронной почте, но `public/smartchild-checklist-oge-ege-informatics.pdf` отсутствует в закреплённой ревизии `main`.

**Критерий закрытия:** реальный PDF включён и проверен, доставка подтверждена тестами; либо обещание убрано до готовности.

## 6. Сборка и тестирование: границы доказательств

Для закреплённой ревизии GitHub Actions CI завершился успешно. Workflow выполняет установку зависимостей через `npm ci`, проверку `npm run check` и production-сборку `npm run build`. Успешный CI не доказывает автоматически реальную доставку почты, отправку PDF, работу формы в production или корректность настроек хостинга.

В предыдущих локальных результатах сообщалось об успешных проверках Astro, сборке 11 страниц и тестах API. Эти результаты необходимо повторить на актуальном рабочем дереве после его инвентаризации. В рамках подготовки этого отчёта локальная среда не запускалась и файлы приложения не менялись.

Фактическое production-развёртывание на Netlify или другом хостинге этим аудитом не подтверждено.

## 7. Рекомендуемый план работ

### Этап 1 — зафиксировать текущее локальное состояние

1. Проверить `git status --short --branch`, текущий HEAD и upstream.
2. Сохранить вывод staged/unstaged diff и список untracked-файлов.
3. Убедиться, что `package.json` и lock-файл не менялись неожиданно.
4. Не удалять и не переносить файлы до завершения инвентаризации.

**Выход:** достоверная карта локальных изменений и подтверждение их сохранности.

### Этап 2 — воспроизвести проверки

1. Запустить имеющиеся тесты API.
2. Выполнить `npm run check` и `npm run build` с согласованной версией npm.
3. Проверить обработку ошибок, валидацию e-mail, конфигурацию окружения и отсутствие секретов в Git.
4. Зафиксировать версии инструментов и точные результаты команд.

**Выход:** повторяемые результаты на одном определённом состоянии файлов.

### Этап 3 — отдельный PR формы и PDF

1. Определить минимальный набор локальных изменений для формы, API, PDF и конфигурации хостинга.
2. Сверить его с текущей `main`, не перенося в PR посторонние изменения.
3. Подготовить отдельный PR с тестами и инструкциями настройки.
4. Не выполнять merge или deploy до проверки.

**Выход:** изолированный, проверяемый набор изменений без смешивания с документационным PR #4.

### Этап 4 — закрыть F1–F3

1. Подтвердить реальные контактные данные либо убрать неподтверждённые.
2. Подключить безопасную форму через POST и протестировать ошибки и защиту.
3. Добавить и проверить PDF и его доставку либо убрать обещание.
4. Приложить доказательства тестирования к PR.

**Выход:** каждый блокер имеет конкретное исправление и проверяемое подтверждение.

### Этап 5 — улучшить качество сайта и CI

1. Добавить автоматические тесты в CI.
2. Исправить структуру заголовков и проверить контраст.
3. Добавить 404 и SEO-метаданные после выбора домена.
4. Проверить реальные URL, HTTPS, поведение формы и доставку на тестовом окружении.

**Выход:** автоматические регрессионные проверки и отдельные подтверждения production-поведения.

### Этап 6 — завершить аудит

1. Сопоставить исправленную ревизию с F1–F23 в первичном аудите.
2. Обновить статусы находок и ссылки на доказательства.
3. После проверки решить, когда PR #4 готов к независимому review и выходу из Draft.
4. Не считать слияние документации доказательством устранения проблем приложения.

**Выход:** трассируемая таблица «находка → исправление → тест/доказательство».
